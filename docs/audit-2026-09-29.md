## 1. Verdict

**The project is well engineered and closer to done than most, but it is not
complete, and two of its headline guarantees are false as shipped.**

What is genuinely strong: the gate is real and green on most legs, the API surface is
robust (6,816 junk requests produced zero 5xx), the docs match the code far better
than usual (all 61 routes documented), authentication, the loopback SSRF guard, path
containment, the boot token and the golden path all check out, and the real desktop
shell boots, spawns its engine and seats a webview.

What is not: the *read-only* command sandbox can be escaped to run arbitrary
commands, one regex can freeze the whole engine, a chat turn can execute repository
code before anyone approves anything, a single formatting slip from a small model
ends a goal, and a rate-limit response ends it too. Those last two matter most for a
product whose target is small local models. Separately, the documented setup does not
work on a stock modern Linux.

## 2. Findings

Severity is my judgement of *impact × likelihood for this product*. `H` high, `M` medium,
`L` low. Line numbers are at `87a926b`.

### 2.1 High

#### H1 — The "read-only" command sandbox can run arbitrary commands and change the repository
`engine/sandbox.py:120` (`_validate_read_only`), `:75` (`DANGEROUS_GIT_FLAGS`), `:95`
(`GIT_LISTING_FLAGS`); `engine/git.py:130`. **Reproduced against real git.**

Invariant 6 and the README both promise a reconnaissance request "can never change the
workspace". Through `SandboxService.run_command(mode="read_only")`, the mode the
librarian and the conductor's `git_history` use:

| Argv (all accepted) | Effect observed |
|---|---|
| `git grep --open-files-in-pa="touch X" one` | **Executed `touch X`.** Arbitrary command execution |
| `git branch -v --del feature-x` | **Deleted the branch** |
| `git branch -v NAME`, `--sort=refname NAME`, `--column NAME` | Created branches |
| `git branch -v -c master copyb` | Copied a branch |
| `git tag --sort=refname NAME`, `--format=x NAME` | Created tags |

Two independent causes. (1) Flags are checked by **exact spelling**, but git accepts
unambiguous *abbreviations* of long options (`--del`, `--open-files-in-pa`), so the
denylist never sees them. The source comment on `-O` shows the authors knew that flag
was dangerous. (2) The "has a listing flag, so it is listing" rule is false for `-v`,
`--sort`, `--column` and `--format`, which are modifiers, not mode switches. The
comment claiming this was "measured" is wrong.

It is reachable: the librarian and the conductor run model-authored argv, and the
model reads untrusted repository text, so a planted README is a prompt-injection route
to code execution. **Aggravated by `git.read_only`** (`engine/git.py:130`), which passes
`env=None` and therefore hands the child the engine's *entire* environment, provider
API keys included; `run_command` filters its environment, `read_only` does not.

What held: a leading global option (`git -c core.pager=id log`) is refused, and
`--no-index` is refused by spelling; its abbreviation `--no-ind` was rejected by *git*
as ambiguous with `--no-indent-heuristic` (I did not enumerate every prefix). That last
protection is luck, not design.

Why the suite did not see this: `tests/test_sandbox.py:154-186` lists the spellings the
authors had already met (`-D main`, `--delete`, `-Oless`, `--open-files-in-pager`,
`--pager=less`) and calls `validate_argv` only. No test runs git, and none tries an
abbreviation or `-v NAME`.

#### H2 — One regex can freeze the entire engine
`engine/library.py:495` (`_search_regex`), reachable from the conductor's `search_code(regex=true)`.
**Reproduced.**

The "per-line" deadline (`PER_LINE_REGEX_SECONDS`) is only checked **between files**. Nothing
bounds a single `rx.search(line)`, and CPython's `re` cannot be interrupted and holds the
GIL. `(a+)+$` against one 28-character line took **13.9 s against an advertised 2.0 s**,
and **the event loop stalled for 14.0 s even though the search ran in `asyncio.to_thread`**.
Each extra character doubles it. A pathological pattern from the model, or a long
minified line in a repository, freezes HTTP, WebSockets, `/health` and Cancel until the
process is killed. Likelihood is low; impact is total.

#### H3 — A chat turn can execute repository code before anything is approved
`engine/executor.py:1160` (`ConductorTools.run_command`), `engine/conductor.py:886` (`BASE_TOOLS`).
**Reproduced in-process.**

`write` refuses unless the goal's stored status is `RUNNING` (invariant 9). `run_command`
has no such gate. On a goal that was `PLANNING` and `plan_only=True`, `run_command(["python3","evil.py"])`
ran the repository's script. The test-mode allowlist also admits `pytest` (which runs
`conftest.py`), `npm run <any script>`, `cargo test` and `go test`, all of which execute
workspace code. `docs/03` §1.4 frames the accepted risk as "approving a goal is approving
the repository's test suite"; a *turn* has no approval step, so asking "what does this
project do?" of a hostile clone can run its code. Note `docs/03:37` still says only the
tester's commands reach `run_command`, contradicting `docs/00` §6.6.

This is a **design decision to make**, not just a bug; the recommendation is in the plan.

#### H4 — One formatting slip from a model fails the goal
`engine/executor.py:556` (`extract_json`), `:853` (`run_agent`). **Reproduced.**

`extract_json` is "first `{` or `[` to last `}` or `]`, then `json.loads`". It fails on:
a `<think>…{…}…</think>` block (Qwen3, DeepSeek-R1, and the README's own `qwen3:8b`
example), an example object before the real one, trailing commas, single quotes, Python
`None`/`True`, and truncated output. `run_agent` then either moves to a fallback target
or, with none configured, raises. **There is no same-model re-ask** ("that was not valid
JSON: <error>; reply again with JSON only"), the standard remedy. Every role's contract is
JSON, so this is the single biggest reliability risk for the stated target of small
local models.

#### H5 — No retry, backoff or `Retry-After` for provider errors, and the reason is discarded
`engine/providers.py:71` (`post_json`), streaming paths at `:544` and `:715`. **Confirmed by search; no retry code exists.**

Any HTTP ≥ 400 becomes a terminal `provider_http` reading `"<label> <status>"`. A 429 or a
529 "overloaded" fails the step; with one provider configured that fails the goal. The
response body, which is where providers say *why* ("credit balance too low", "model not
found", "context too long"), is dropped, so users see `anthropic 400`.

#### H6 — The documented UI test toolchain is wrong, so the gate cannot run
`ui/tests/tsxLoader.ts`, `README.md` ("Node 22.6+"), `Makefile`. **Reproduced.**

On Node 22.22.2, 161 of 1,110 UI tests fail with `ERR_VM_MODULE_LINK_FAILURE: request for
'./fallback/encoding.js' … not been linked`, all from one cause: the suite's custom loader
uses async `module.register` hooks, and jsdom 30's CJS `require()` of an ESM dependency
(`@exodus/bytes`) cannot link under them. On Node 24.21.0 all 1,110 pass. jsdom 30
itself declares `^22.22.2 || ^24.15.0 || >=26`, so Node 22 *is* nominally supported.
`package.json` has no `engines`, and nothing checks the version before running.

## 5. Completion plan

Ordered so each phase makes the next one safer. Sizes: **S** under half a day, **M** 1–2 days,
**L** 3–5 days. The project's own rules apply throughout: every engine change ships with a
test that fails without it, no test skips itself out of a guarantee, and a documented contract
changes in the same commit as its code.

The recurring root cause behind H1, M3 and M6 is worth naming, because fixing findings
one at a time will not stop the next one: **tests construct the model or assert the
spellings already known, instead of driving the boundary** (`GoalCreate(...)` not
`POST /goals`; `validate_argv` on known-bad strings, never real git; a hydration guard the
design comments describe but no test races). Phase 1 therefore adds boundary-level tests,
not just fixes.
